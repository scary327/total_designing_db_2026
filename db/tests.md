# Протокол проверки FoodExpress

Проверено 15.11.2026 на PostgreSQL 17.6 в отдельном временном кластере Linux.
SQL-скрипты собраны с нуля. Архив восстановлен в другую пустую БД;
проверки выполнены с подключением пользователя `inspector`.

## Сборка и архив

1. В подготовленной БД созданы `exts` и расширение `uuid-ossp`.
2. Последовательно выполнены `db/schema/00_schema.sql`–`09_how_much_money.sql` и `grants.sql` с `ON_ERROR_STOP`.
3. Под `inspector` вызвана `insert_test_data(10)`.
4. Создан архив `pg_dump -Fc -n kalugin_food --no-privileges`.
5. В другой БД подготовлено расширение, выполнены `pg_restore --no-owner --exit-on-error` и `grants.sql`.
6. Schema-only дампы исходной и восстановленной БД совпали. При сравнении исключены случайные служебные токены `\restrict`/`\unrestrict` самого pg_dump.

Архив создан PostgreSQL 17; для восстановления требуется `pg_restore` версии 17 или новее.

## Выполненные проверки

| Скрипт | Результат |
|---|---|
| `db/checks/foreign_keys.sql` | Удаление используемых клиентов, адресов, привязок адресов, курьеров, ресторанов, категорий и блюд отклоняется. Удаление заказа удаляет его позиции, оплаты и отзывы; клиент и блюда сохраняются |
| `db/checks/smoke.sql` | Двойная очистка и два вызова генератора: по 20 клиентов, курьеров, ресторанов и категорий, по 100 адресов, блюд, заказов, отзывов и оплат. Проверены суммы, статусы, необязательный комментарий, add_product, рейтинг, зарплата и статистика |
| `db/checks/integrity.sql` | Среднее оценок 3/4/5 равно 4; после удаления оценки 3 равно 4,5; перенос отзыва пересчитывает обе сущности; без отзывов рейтинг NULL. Промежуточный месяц без доставок сохраняется в отчёте |
| `db/checks/regressions.sql` | Чужое блюдо и несовместимая смена ресторана заказа/блюда отклонены. В составе нет restaurant_id. Обычное и массовое обновление отзывов пересчитывают среднее даже при произвольном пользовательском параметре skip_rating |
| `db/checks/regressions.sql` — оплаты | При проверке отложенных ограничений отвергаются удаление/порча успешной оплаты доставленного заказа и перевод неоплаченного заказа в доставленный. Вторая успешная попытка запрещена уникальным индексом. Замена успешной попытки в одной транзакции допустима |
| `db/checks/salary_boundaries.sql` | Проверены 0/150/151/250/251/500/501 доставок. Начальный коэффициент 0,3 даёт выплату 30 рублей за доставку с комиссией 100 рублей. Повторный расчёт сохраняет применённый коэффициент. Уволенный получает выплату без смены коэффициента; курьер с будущей датой найма выплаты не получает |
| `db/checks/template_checks.sql` | Выполнены запросы проверки структуры, enum, связей, количеств, сумм, статусов, рейтингов, отчётов и прав из шаблона. Скрипт завершился без ошибок; проверки данных не выявили расхождений |
| `db/checks/concurrency.py` | Три двухсессионных сценария для рейтинга, оплаты и ресторана проверены при READ COMMITTED и REPEATABLE READ. Согласованный пересчёт проходит; несовместимое изменение отклоняется с 23514, а запись по устаревшему снимку — с 40001. После сценариев расхождений нет |
| Повторный `grants.sql` | Пароль существующей роли сохраняется; default privileges для будущих объектов не выдаются |

В функциональном прогоне получены 3 ожидающих, 95 оплаченных и 2 ошибочных
заказа. Количества случайны; проверяется согласованность статусов и оплат.
Проверки шаблона дополняются явными исключениями в функциональных скриптах:
само выполнение SELECT без SQL-ошибки не считается доказательством корректности данных.

**Скрипты предназначены только для отдельной тестовой БД.** `smoke.sql`,
`template_checks.sql` и `concurrency.py` очищают данные. `foreign_keys.sql`,
`integrity.sql`, `regressions.sql`, `salary_boundaries.sql` выполняют изменения
в откатываемой транзакции. Отложенные ограничения проверяются явно через
`set constraints all immediate` до отката.

Пример запуска для уже восстановленной тестовой БД:

```sh
psql -U inspector -d foodexpress_test -v ON_ERROR_STOP=1 -f db/checks/regressions.sql
psql -U inspector -d foodexpress_test -v ON_ERROR_STOP=1 -f db/checks/salary_boundaries.sql
PGDATABASE=foodexpress_test python3 db/checks/concurrency.py
```

Конкурентный тест использует только стандартную библиотеку Python и `psql`.
Его управляющее соединение должно видеть `pg_stat_activity`, чтобы подтвердить
ожидание блокировки; изменения данных выполняются под `inspector`. Проверка
40001 означает безопасный отказ транзакции с устаревшим снимком, а не её
автоматический повтор приложением.

## Генерация и производительность

На чистых таблицах `insert_test_data(1000)` создала по 1000 строк справочников
и по 5000 адресов, блюд, заказов, отзывов и оплат за 1,713 с. Повторный вызов
с тем же аргументом добавил ещё одну порцию за 1,717 с. В результате —
10000 заказов и 10000 блюд. Цены блюд 100–1500 рублей, суммы блюд заказов
1000–11880 рублей. Замер включает запуск psql и завершение транзакции.
Это локальные результаты, а не гарантия времени для других машин и объёмов.
Полномасштабный прогон на миллион строк не выполнялся.

В генераторе ФИО задаётся длинами 1–50 для varchar(50). Граничная длина
проверена отдельным сценарием; маленькая случайная выборка не обязана
содержать каждую возможную длину.

## Выбор лидеров в статистике

`get_statistic` использует `array_agg` с сортировкой и выбором первого элемента.
Альтернатива для сравнения — `db/checks/statistic_alt.sql`: групповой максимум,
соединение с максимумом и случайный выбор при равенстве. При
сравнении на 1000 ресторанах и 5000 заказах после ANALYZE, jit=off, по 30 вызовов
дали 0,419564 с и 0,419511 с соответственно. Заметного преимущества одного
варианта замер не показал. В реализации сохранён вариант с массивом;
для обоих способов нужно сохранять группировку по идентификатору и случайный
выбор при одинаковом числе заказов или количестве блюд.

## Трактовка оплат

Незавершённый или отменённый заказ может пока не иметь успешной попытки.
Доставленный заказ обязан иметь успешную оплату на момент завершения транзакции.
Более одной успешной попытки для одного заказа не допускается. Проверка в конце
транзакции позволяет сначала вставить заказ, затем его оплату, а также заменить
попытку несколькими операторами до COMMIT.
