# Протокол проверки FoodExpress

Проверки ниже выполнены 15.11.2026 в отдельном временном кластере PostgreSQL 17.6
на Linux. Проверки выполнялись в изолированной тестовой базе.

## Сборка и восстановление

1. Создана пустая БД, в ней — `exts` и расширение `uuid-ossp`.
2. Без ошибок выполнены `db/schema/00_schema.sql` … `09_how_much_money.sql` и `grants.sql`.
3. Под `inspector` выполнена `CALL insert_test_data(10)`.
4. Создан архив `pg_dump -Fc -n kalugin_food --no-privileges`. Архив PostgreSQL 17 совместим с `pg_restore` версии 17 или новее.
5. В другой чистой БД созданы `exts` и `uuid-ossp`, архив восстановлен с `pg_restore --no-owner --exit-on-error`, после чего запущен `grants.sql`.
6. В восстановленной БД пройден `db/checks/smoke.sql` под `inspector`.

**Внимание:** `db/checks/smoke.sql` вызывает `erase_test_data()` и удаляет данные
во всех таблицах схемы. Запускать его только на отдельной тестовой копии.

## Результаты

| Проверка | Результат |
|---|---|
| Двойная очистка и два вызова `insert_test_data(10)` | Без ошибок; 20 клиентов, курьеров, ресторанов и категорий; по 100 адресов, блюд, заказов, отзывов и оплат |
| Суммы заказов | Нарушений `order_amount >= 1000`, `total_amount >= 1000` и формулы комиссии в генераторе не обнаружено |
| Статусы и суммы оплаты | Сумма каждой попытки равна итогу заказа; статус заказа соответствует попытке; доставленные заказы оплачены. В одном прогоне получено 3 ожидающих, 89 оплаченных и 8 ошибочных заказов |
| Комментарий заказа | Обновление на `NULL` и на пустую строку выполнено без ошибки |
| `add_product` | Добавление прошло; отрицательная цена и отсутствующий ресторан отклонены ограничениями БД |
| Рейтинги | Изменение оценки пересчитало среднее; в откатываемой транзакции перенос отзыва с блюда на ресторан пересчитал оба рейтинга |
| `courier_salary` | Два последовательных вызова выполнились без ошибок; расхождений выплат с комиссией доставленных заказов не обнаружено |
| `get_statistic` | Число строк равно числу ресторанов; суммы сверены с независимым запросом, расхождений нет |
| Внешние ключи | `db/checks/foreign_keys.sql` проверяет защиту связанных записей и каскадное удаление зависимых строк заказа в откатываемой транзакции |
| `grants.sql` | Два повторных запуска не изменили пароль существующей роли; запись в `pg_default_acl` для схемы не появилась |

В отдельных прогонах процедура также создала порцию из 1000 клиентов и
5000 заказов. В `db/checks/template_checks.sql` выполнены 50 проверок по `templates/tests.md`. Проверка E.1 передаёт идентификаторы через `\gset`; E.2–E.4 выполняются в `smoke.sql` и `integrity.sql`. Последний тест работает в транзакции и откатывает изменения.

## Сравнение способов выбора лидеров

В отдельной тестовой БД создали альтернативу `db/checks/statistic_alt.sql`:
вместо `array_agg(...)[1]` — максимум по группам, соединение с максимумом и
`DISTINCT ON` со случайной сортировкой при равенстве. После `ANALYZE`, с
`jit=off`, на 1020 ресторанах и 5100 заказах попеременно выполнили оба
варианта по 30 раз. Суммарное время: массив — 0,433 с, максимум с JOIN —
0,444 с. Это приблизительный локальный замер, не гарантия для других объёмов
и планов. В функции используется вариант с массивом: он сохраняет
случайный выбор при равенстве и не требует повторной агрегации и соединения.
Для воспроизведения в отдельной БД выполните `statistic_alt.sql`, затем:

```sql
SET search_path TO kalugin_food, exts;
ANALYZE;
DO $$
DECLARE started timestamptz; i integer; array_time interval := interval '0'; join_time interval := interval '0';
BEGIN
    FOR i IN 1..30 LOOP
        started := clock_timestamp(); PERFORM * FROM get_statistic();
        array_time := array_time + clock_timestamp() - started;
        started := clock_timestamp(); PERFORM * FROM benchmark_statistic_alt();
        join_time := join_time + clock_timestamp() - started;
    END LOOP;
    RAISE NOTICE 'array: %, max+join: %', array_time, join_time;
END $$;
```

## Статусы оплаты

В BR-8.1 формулировка «ровно одна успешная оплата» расходится с BR-8.7,
который предусматривает ожидающие и ошибочные оплаты. В тестовых данных у
незавершённого или отменённого заказа успешной попытки может не быть;
у доставленного она есть. Частичный уникальный индекс не допускает более одной
успешной попытки для заказа.
